From Local-First to Full-Stack

I've always been a fan of local-first software. Applications that work offline, store data locally, and don't depend on an internet connection have always appealed to me.

But eventually, I realised that not every application can work that way.

Some software genuinely needs a database, authentication, synchronisation, and proper backend infrastructure. That got me thinking: why not build one myself?

And that's how I started working on my first production-oriented full-stack web application.

From Local-First to Something Bigger

I've previously worked on several web applications and projects, including CampusCrave. However, building something with a proper backend, persistent database, authentication, and remotely accessible infrastructure introduces an entirely different set of challenges.

I wanted to build something that wasn't just a frontend demonstration or a website that looked good in screenshots. I wanted something that could actually be used.

For this project, I chose Next.js as the application framework and Firebase for database infrastructure.

The combination gave me the flexibility I needed without having to build and maintain every piece of backend infrastructure from scratch.

But getting everything connected was only the beginning.

The Reality of Building Full-Stack Software

One thing I quickly discovered was that building a full-stack application isn't necessarily difficult because of the code itself.

It's everything around the code.

Database configuration, authentication, access permissions, deployment, environment variables, hosting limitations, free-tier restrictions, paywalls, and security considerations all become part of the development process.

Things that seem straightforward in a local development environment can become surprisingly complicated when you try to make them accessible to actual users.

There were limitations I hadn't initially considered. Some services had restrictions, some features came with additional costs, and certain architectural decisions required more thought than I expected.

I had to work around these constraints, reconsider approaches, and make the most of the tools available to me.

It wasn't always smooth, but that's probably what made the experience worthwhile.

Security Wasn't Something I Could Compromise On

This was probably the most important part of the entire project.

When software starts handling user accounts and remotely stored information, the responsibility changes significantly.

A database isn't just somewhere to store application data. It's potentially one of the most sensitive components of the entire system.

An incorrectly configured database can expose private information, allow unauthorised users to access other people's records, or even create pathways to account compromise.

I didn't want to build something that worked perfectly on the surface while leaving fundamental security problems underneath.

So I spent considerable time looking into authentication, authorisation, database access policies, input handling, and other security considerations.

I also conducted a dedicated security audit covering areas such as:

- Authentication and authorisation.
- Cross-site request forgery (CSRF).
- Cross-site scripting (XSS).
- SQL injection and command injection.
- Cryptographic practices.
- File upload security.
- API security and defensive programming.

The audit was read-only, and I wanted to understand the application's actual security posture rather than simply assume that using established technologies made it secure.

I'm still working through improvements. Security isn't a checkbox you tick once and forget about. It's an ongoing responsibility.

Building Faster With AI, but Thinking Like a Developer

Another interesting aspect of this project was my use of AI-assisted development.

Tools commonly associated with vibe coding have changed how quickly I can turn an idea into something functional.

Tasks that might previously have taken days can sometimes be completed in hours. Prototyping, exploring different implementations, debugging, and iterating on interfaces have become considerably faster.

I don't see AI as a replacement for understanding software development, though.

If anything, it makes understanding the underlying architecture more important.

Generating code is one thing. Knowing whether that code is secure, maintainable, efficient, and appropriate for the application is another.

I still want to understand what I'm building, why I'm building it that way, and what could go wrong.

AI helped accelerate the process, but the architectural decisions and responsibility for the final product still matter.

One Day. One Major Milestone.

Getting the application to this stage in approximately one day was something I genuinely didn't expect.

I've built countless full-stack applications and experimented with several ideas before. Some never made it to release, while others were developed in different contexts where I wasn't necessarily the person publicly credited for the work.

This project felt different.

It was something I could build, own, iterate on, and present as part of my developer portfolio.

It's not perfect. I know that. There are still improvements to make, limitations to address, and features I'd like to refine.

But it's functional, it's a substantial step forward, and I'm genuinely proud of what I've accomplished.

What's Next?

My long-term goal is to become a stronger full-stack developer.

I already have experience working across different parts of application development, but I don't want to stop at knowing how to connect a frontend to a database.

I want to understand infrastructure, security, deployment, scalability, performance, and the engineering decisions that make software reliable in the real world.

This project is another step in that direction.

I'm going to keep improving it, auditing it, and making it better. I don't necessarily expect perfection, but I do want to get as close as practical.

Building software isn't just about making something that works. It's about making something people can trust.

And that's probably the biggest lesson I took away from building my first production-oriented full-stack application.
